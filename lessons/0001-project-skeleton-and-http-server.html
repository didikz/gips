Project skeleton & HTTP server

~20 min · stdlib only · first runnable increment

Mission: Ship a production-grade image processing service. Today: a health-checked HTTP server with idiomatic package layout — the foundation every later endpoint builds on.

What you already know vs. what changes

In Go — especially while learning — net/http is enough. Effective Go argues for clarity over cleverness: small packages, explicit wiring, errors returned not thrown.

This lesson is the first step toward the full image processing spec — built flat, no framework layers.

Package layout

See the full reference: project layout.

cmd/gips/main.go              → entry point (thin)
internal/httpserver/server.go → mux + ListenAndServe
internal/http/handler/health.go → GET /healthz
internal/config/config.go     → PORT from env

Why internal/? Go enforces that other modules cannot import it. Your domain logic stays private; only cmd/ is the public entry.

The server pattern

Three layers, each with one job:

  1. config — read environment (defaults for local dev).
  2. handler — pure HTTP functions; no global state.
  3. server — register routes, own the http.Server.

The health handler is deliberately boring — production services need a liveness probe:

// internal/http/handler/health.go
func Health(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusOK)
    io.WriteString(w, `{"status":"ok"}`)
}

Register it on a ServeMux (Go 1.22+ supports method-aware patterns):

mux := http.NewServeMux()
mux.HandleFunc("GET /healthz", handler.Health)

Effective Go reminders

  • Run go fmt ./... — formatting is not negotiable.
  • Exported names start uppercase (Health); package-local names stay lowercase.
  • Doc comments on exported symbols: // Health reports service liveness.
