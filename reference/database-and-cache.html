Database & cache stack

SQLite · Redis · local disk for blobs

Three storage layers

LayerTechnologyStores
Relational SQLite (database/sql + modernc.org/sqlite) Users, sessions/tokens metadata, image records, transform history
Blob files Local filesystem (data/images/) Original and derived image bytes (until optional S3/R2 lesson)
Cache Redis (redis/go-redis/v9) Hot transformed images (keyed by image ID + transform hash), optional rate-limit counters

Why SQLite?

  • Zero ops for learning — one file, no server process.
  • Plain database/sql: open DB in main, pass *sql.DB to handlers and store functions.
  • SQL lives in internal/store/ as simple functions — no ORM, no repository layer.

Why Redis (and when)?

Redis arrives in lesson 10, after transforms work without cache. You'll implement cache-aside:

  1. Check Redis for transform:{imageID}:{hash}
  2. On miss — run transform, store bytes in Redis with TTL, return response
  3. On hit — serve from Redis, skip CPU-heavy work

This matches the roadmap.sh tip on caching transformed images.

Flat data access

// internal/store/user.go
func CreateUser(ctx context.Context, db *sql.DB, username, hash string) (User, error)
func UserByUsername(ctx context.Context, db *sql.DB, username string) (User, error)

// handler calls store directly
user, err := store.CreateUser(r.Context(), h.db, username, hash)

Extract a function when you repeat SQL. Introduce an interface only when a second implementation exists (e.g. tests with fakes) — not upfront.
